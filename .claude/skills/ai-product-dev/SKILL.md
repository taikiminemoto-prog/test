# 実践AI開発術：完成までの11ステップ

PIVOTの動画「非エンジニアのための『実践AI開発術』：完成までの11ステップ」（ゲスト: 梶谷健人さん）の進め方を、Claudeがそのまま実行できる手順にしたもの。動画全体の要約は `references/video-summary.md` にある。

## 前提となる考え方

**作るのはAI、決めるのは人間。** 動画の締めくくりの主張。AIに任せられることと、本人にしかできないことの線ははっきりしている。ユーザーにしか決められないのは次の4つ。

1. 何を作るか（コンセプト）
2. 価値があるか（価値検証の結果を受けて、続けるか）
3. 価格
4. 重要な仕様の分かれ道

この4つをClaudeが黙って決めると、作り込むほど手戻りが大きくなるうえ、ユーザーの事業の判断そのものを奪ってしまう。だからClaudeは選択肢と推奨を用意して判断を仰ぐ。それ以外（文書化、画面、実装、テスト、素材づくり、計測）はClaudeが自分で手を動かして前に進める。

**順番と、難所ごとの型がある。** 11ステップを順に進め、各ステップの「難所のポイント」を押さえれば、非エンジニアでもリリースできる品質に届く。順番を飛ばす（価値を確かめる前に本番を作り込む、デザインのルールを決める前に画面を塗る）と、手戻りが大きくなる。

## 始め方

1. **現在地を確かめる。** `docs/product/PROGRESS.md` があれば読み、どのステップまで進んだか、何が決まっているかを把握してから続ける。
2. **なければ、相談の種類で分ける。**
   - 新しいプロダクトを作る話: 専用のフォルダ（リポジトリ）で始める。動画が言うとおり、フォルダがAIの仕事場になるので、別のプロダクトのリポジトリの中で始めそうなときは、新しいフォルダを作るかユーザーに確かめる。`assets/PROGRESS.md` を `docs/product/PROGRESS.md` に写し、ステップ1から。
   - 既存のプロダクトの個別の相談（価格、デザイン、根深いバグ、セキュリティ、計測など）: 下の表で該当するステップを見つけ、その参照ファイルだけを読んで実行する。11ステップ全体を押し付けない。
3. **ステップに入るたびに、対応する参照ファイルを読む。** ポイントと成果物の型はそこにある。

例:
- 「家計簿のAIアプリを作りたい」→ 新規。ステップ1の聞き取りから始め、足りない点を3つまで質問し、01-concept.md の下書きを作って、狙う領域に入っているかを確かめ、進めるかをユーザーに決めてもらう。
- 「このバグ、何回直しても再発する」→ ステップ6の「根深いバグ」の型。すぐには直さず、原因と解決案を説明して選んでもらう。

## 全ステップに共通する進め方

### ユーザーに決めてもらうとき
- 背景を2〜3行、選択肢を2〜4個（それぞれ、何が起きるか・良い点・気になる点）、推奨とその理由、最後に質問、の順で短く出す。
- 文字で比べられるものは、選択肢の質問（AskUserQuestion などが使えればそれ）で聞く。見た目や言い回しの違いが大事なもの（デザイン案、文言、微妙な仕様案）は、次の判断用ページを作って見て選んでもらう。
- ユーザーが「任せる」と言ったら推奨で進め、そのことも記録する。

### 判断用ページで、見て決めてもらう
チャットの文章だけでは、デザイン案や文言の違いは判断しにくい。AIはWebページをほとんど手間なく作れるので、判断のための使い捨てのページを作り、ユーザーは選ぶだけにする。部下のデザイナーが案を並べ、社長が選ぶ感覚。
- `assets/decision-page.html` を `docs/product/decisions/<日付>-<テーマ>.html` に写し、ファイル冒頭の `DATA` を書き換える。見た目を見せたい案は `preview_html` にHTMLを入れる。
- 開き方を伝える。手元のPCならブラウザで開いてもらう。クラウドの環境で、Artifact のようにページを公開して見せる手段があればそれを使う。
- ユーザーは選んで「結果をコピー」を押し、チャットに貼る。選ばれたものだけを実装し、PROGRESS.md に記録する。

### 品質の基準を、外の物差しで示す
「かっこよく」「いい感じに」は基準が曖昧で、AIはどこで止めていいか分からず、ほどほどで止まってしまう。外にある具体的な物差しを置く（例: デザインなら Awwwards・FWA・Webby Awards を取れる水準）。自分の成果物がそこに届いているかを自分で判定し、足りなければ自分で磨いてから見せる。マネジメントで「どこまでやるか」を示すのと同じ。

### 下の層から積む
UXの5レイヤー（戦略 → 要件 → 構造 → 骨格 → 表層）の順に決め、上の層は下の層と矛盾させない。全部を同時に考えると、何から決めればいいか分からなくなる。

### Webを先に作る
スマホアプリが目的でも、まずスマホ幅のWebで作って、機能と見た目を確かめる。ネイティブアプリは、ビルドして端末に入れて確かめる往復が重い。AIはWebからネイティブへの「翻訳」が得意なので、Webで作った分は無駄にならない。

### 作った本人とは別のAIに、厳しくレビューとテストをさせる
自分が書いたものの穴は、自分では見落としやすい。性格の違うAIに見させる（動画では Claude Code が作り、Codex が厳しく見る）。やり方は references/06-production.md。

### 根深い問題は、直す前に原因と案を説明する
表面だけ直すと、別の問題を生む。根本原因と解決案を分かりやすく説明し、ユーザーが方針を選んでから直す。

### 小さく、速く、何度も
1つのプロダクトは、集中すれば3週間ほど（合宿のように集中すれば2週間ほど）が目安。最初に出す範囲はその大きさに収め、出してから学ぶ。「AIで誰でも作れる」は半分本当で半分うそで、作りたいという強い意思がないと途中で飽きる、と動画は言う。区切りごとに「進んだこと」と「次の一手」を短く伝え、勢いを保つ。

### 説明は、非エンジニアに伝わる言葉で
動画の想定する読み手は非エンジニア。専門用語は避けるか一言で補い、判断に必要なことだけを短く伝える。

## 大きな実装の進め方（ステップ4・6）
- 計画と統合は、メインのセッションが担う（動画では、最も賢いモデルの Fable が全体の計画と管理をしている）。作業を互いに独立した単位に分け、つなぎ目（データの形、APIの形）を先に決める。
- 独立した作業は、サブエージェント（Opus や Sonnet）に並列で任せる。メインが取りまとめてテストし、これを繰り返す。
- 小さな変更は分けない。分ける手間のほうが大きくなる。
