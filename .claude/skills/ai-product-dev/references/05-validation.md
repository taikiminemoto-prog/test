# ステップ5: 価値検証

プロトタイプの段階で、「このサービスはいける」と確信を持てるかを確かめる。観点は2つだけ。

1. **コアユーザーが毎日使うか、使いたくなるか。** ユーザー自身がいちばんの利用者なら本人。誰か他の人のためのサービスなら、その人。
2. **実際に使ってもらい、「このサービスがなくなったら、どのくらい困りますか？」を5段階で聞く。** 「非常に困る」が過半数なら、いける。

## アンケート（そのまま使える）

```
Q1. このサービスが使えなくなったら、どのくらい困りますか？
    5 非常に困る / 4 困る / 3 どちらとも言えない / 2 あまり困らない / 1 まったく困らない
Q2. （自由回答）いちばん役に立っているのは、どんな点ですか？
Q3. （自由回答）もしなくなったら、代わりに何を使いますか？
Q4. （自由回答）どんな人にいちばん役に立つと思いますか？
Q5. （自由回答）何があれば、もっと使いますか？
```

判定に使うのはQ1だけ。Q2〜Q5は次の改善のヒントにする。

補足: これは、「なくなったらどのくらい残念か」を聞いてプロダクトが市場に合っているかを見る Sean Ellis のテストと同じ系統の問い。動画の基準は、5段階で「非常に困る」が過半数。

## 集計と記録

`docs/product/05-validation.md` に次を残す。

- 誰に、何人に、どれくらいの期間使ってもらったか
- Q1の分布と「非常に困る」の割合。人数も必ず書く（10人程度までは傾向として扱う）
- 毎日使われているか（利用の記録があれば数字で）
- Q2〜Q5のまとめと、次に直すこと

## 基準に届かなかったら

回答から足りないものを分析し、選択肢を出す（対象者を絞り直す / 中心の体験を変える / コンセプトに戻る）。続けるか、方向を変えるかはユーザーが決める。基準に届かないまま本番を作り込むと、使われないものの完成度を上げることになる。

## 完了の条件

2つの観点で「いける」とユーザーが判断した。または、届いていないことを承知のうえで進むと決めた。
