# ステップ9: セキュリティ

自分が作ったものに穴がないかは怖い。理想は、セキュリティに詳しいシニアのエンジニアに見てもらうこと。その前に必ずできることとして、AIに攻撃者の立場で一通り攻撃させ、攻撃が通ったところを全部直す（ペネトレーションテスト）。最新のモデルはセキュリティの能力がとても高いので、これだけでかなりの穴が塞がる。合言葉は「ペネトレーションテストして」。

## 守ること

- 攻撃してよいのは、このプロダクトの手元の環境とテスト用の環境だけ。本番の環境、他人のサービス、外部のAPIには行わない。決済はテストモードで。
- 見つけた問題は、直すまでリポジトリの外に出さない（公開のissueなどに書かない）。

## 進め方

1. 攻撃される入口を洗い出す: 公開しているページとAPI、ログイン、権限、入力欄、ファイルのアップロード、Webhook、AIの機能、管理画面、秘密の情報（APIキーなど）、使っているパッケージ。
2. 下のチェックリストの観点ごとに、実際に攻撃を試す。試した手順と結果を残す。
3. 重大な順に `docs/product/09-security.md` に書く: 何が、どうすれば、どうなるか（再現手順）、影響、直し方。
4. 直す → 同じ攻撃をもう一度試して、塞がったことを確かめて記録する。
5. 診断は、直す本人とは別のAI（新しいサブエージェントや Codex）にやらせると、見落としが減る。

## チェックリスト

- ログイン: なりすまし、パスワードの総当たり、セッションやトークンの扱い
- 権限: URLやIDを書き換えるだけで、他人のデータを見たり変えたりできないか。一般の利用者が管理機能に入れないか。データベースの行ごとの権限（例: Supabase の RLS）
- 入力: SQLなどの注入、XSS、サーバーに外部のURLを読ませる攻撃（SSRF）、ファイルのパスの操作、危険なファイルのアップロード
- 秘密の情報: APIキーが、画面側のコード、リポジトリ、ログに出ていないか
- 決済: 金額の書き換え、Webhookの署名の確認、二重の処理、有料の機能が使えるようになる条件
- AIの機能: 指示の上書き（プロンプトインジェクション）、隠している指示文の漏えい、他の利用者のデータの混入、大量に呼び出してAIの費用を膨らませる攻撃、AIの出力をそのままHTMLとして表示していないか
- 乱用: 回数の制限、大量の登録、無料枠の使い回し
- パッケージ: 既知の脆弱性（`npm audit`、`pip-audit` など）
- 設定: CORS、セキュリティ用のHTTPヘッダ、HTTPS、エラー画面で内部の情報を出していないか

## ユーザーが決めること

直せない、または直さずに残すリスクがあれば、その中身と影響を説明し、受け入れるかを決めてもらう。個人情報、決済、医療など影響の大きいサービスでは、専門家のレビューも勧める。

## 完了の条件

- 見つかった重大・中程度の問題がすべて直り、同じ攻撃で塞がったことを確かめた。
- 残すリスクを、ユーザーが承知している。
