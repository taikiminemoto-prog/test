# ステップ6: 本番実装

基本は「どんどん作っていく」でよい。押さえるポイントは5つ。

## 1. 作ったAIとは別のAIに、厳しくレビューとテストをさせる

動画では、Claude Code はクリエイティブ型（アイデアがよく、デザインの感覚も高い）、Codex はコードが厳密でバグをよく見つける型（ただし柔軟さやデザインの感覚は弱い）と見ている。そこで Claude Code に作らせ、Codex に絶えず厳しくテストとレビューをさせる。人の開発で、タイプの違う人同士がレビューし合うのと同じ構造。

このスキルでの実行:

- `command -v codex` で Codex CLI があるか確かめる。あれば、非対話の実行（`codex exec` など。使い方は `codex --help` で確認）で下の依頼文を渡し、厳しいレビューとテストを頼む。コードを別のサービスに送ることになるので、初めて使うときに一度だけユーザーの了承を取る。
- なければ、実装にかかわっていない新しいサブエージェント（できれば別のモデル）に、厳しいレビュアー役を任せる。`/code-review` のようなレビュー用のスキルがあれば、それも使う。
- 指摘は鵜呑みにせず、本当に起きるかを確かめてから直す。直したら、もう一度レビューを通す。

依頼文の例:

> あなたは厳しいシニアエンジニア兼テスター。仕様（docs/product/02-scope.md、02-structure.md）と今回の変更を照らし合わせ、バグ、仕様の抜け、境界の条件、セキュリティ、テストの不足を、重大な順に挙げて。それぞれに再現手順と根拠を付けて。良い点の説明はいらない。テストを書いて動かせるものは、実際に動かして確かめて。

## 2. 役割を分ける（大きな実装のとき）

動画では、最も賢いモデル（Fable）が全体の計画と管理をし、速いモデル（Opus、Sonnet）がサブエージェントとして並列に実装し、それを Fable が取りまとめる、を繰り返している。こういう体制でやりたい、とAIに伝えればその形で動ける。SKILL.md の「大きな実装の進め方」に従う。

## 3. 決済のような重い機能も、AIに実際に通させる

決済は失敗が許されず、毎回人が手で試すのは大変。最後の最後は人が確認するが、その手前の検証はAIが一通りやる。

- Stripe ならテストモードで、テスト用のカード番号を使う（例: 4242 4242 4242 4242 は成功、4000 0000 0000 0002 は拒否、4000 0025 0000 3155 は本人認証あり。最新の一覧は Stripe の公式ドキュメントで確認）。
- ブラウザ操作（Playwright など）で、申し込み → 支払い → Webhook → 有料の機能が使えるようになる、までを通す。解約、支払いの失敗、二重の送信も試す。
- iOS のアプリ内課金は、StoreKit のテスト環境やサンドボックスで確かめる。
- 本物のカードや本番の環境では試さない。

## 4. 根深いバグは「原因の説明 → 解決案 → ユーザーが選ぶ → 直す」

根深い問題を表面的に直すと、別の問題を生む。重いバグは、AIに任せきりにせず人が関わったほうがうまくいくことが多い。動画のゲストは、次の趣旨の依頼文をすぐ呼び出せるように登録している。

> 問題の根本原因を分析して、根本的な解決方法を分かりやすく提案して。まだ実装はしないで。

根深そうだと判断する目安: 同じ所を2回以上直しても再発する、原因がはっきりしない、複数の場所にまたがる、直し方によってデータや課金に影響する。

そう判断したら、すぐには直さず、次の形で報告して、ユーザーが選んでから直す。

1. 何が起きているか（症状）
2. 根本原因（根拠となるログ、コード、再現手順）
3. 解決案 A / B（/ C）: やること、影響する範囲、リスク、手間
4. 推奨とその理由

ユーザーが上の依頼文と同じ趣旨のことを言ったときも、この形で答え、実装はしない。

## 5. AIチャットのように操作が無限にある機能は、テストシナリオ表で守る

AIチャットは、原理的にユーザーが無限通りの操作をできるので、すべてを確かめきることはできない。それでもできることはある。想定される使い方の範囲を前もってテストシナリオ表にしてAIに作らせ、そのすべてをAIに実行させる。AIを使ったプロダクトでは欠かせない工程。

`docs/product/06-test-scenarios.md`:

| ID | 想定する人・状況 | 入力（会話の流れ） | 期待する振る舞い | だめな例 | 結果 |
|---|---|---|---|---|---|

入れておきたい観点（補足）: 典型的な使い方 / 短すぎる・曖昧な入力 / 対象外の質問 / 医療・お金・法律など慎重さが要る話題 / 指示を上書きしようとする入力（プロンプトインジェクション）/ 個人情報 / 長い会話 / 英語など他の言語 / 連続した送信 / AIのAPIが失敗・遅延したとき。

判定のしかた: はっきり決められるもの（文字数、禁止語、形式）はコードで判定し、言い回しの良し悪しは別のAIに採点させる。結果を表に書き、だめだったものを直して、もう一度全部を回す。AIのモデルや指示文を変えたら、そのたびに回し直す。

## 完了の条件

- 別のAIのレビューの指摘が解消され、テストが通る。
- 決済などの重要な流れが、テストの環境で端から端まで通る。
- AIの機能があれば、テストシナリオ表の全件が合格している。
